# Задача Cursor: построить маршрутную архитектуру MLM Academy

Работай внутри текущего репозитория MLM Academy. Это архитектурная миграция существующего проекта, а не создание нового сайта.

## 0. Цель

Нужно один раз построить backend и внутреннюю структуру, чтобы:

1. все 112 стабильных Track ID уже существовали в едином реестре;
2. каждый ID разрешался по своему типу сущности;
3. активные переходы вычислялись Route Engine по структурированному outcome, а не были захардкожены в HTML каждого трека;
4. новый готовый трек в будущем подключался одним стандартным пакетом без ручной переделки соседних страниц;
5. публичный каталог и поиск могли знать о метаданных треков;
6. полный контент, прогресс, маршрутные кнопки и переходы оставались закрыты до серверно подтверждённого права доступа;
7. платежи и платная навигация сейчас оставались выключенными.

Не создавай содержание отсутствующих треков. Не превращай 112 ID в 112 одинаковые HTML-страницы. Не включай оплату. Не деплой в production без отдельной команды.

## 1. Сначала проведи read-only аудит репозитория

До изменения кода:

- определи фактический стек, структуру приложения, backend, хранилища и способ деплоя;
- найди реализацию каталога, поиска, страницы `/track`, A2-008, Members/авторизации, маршрута пользователя и текущего localStorage;
- найди все способы построения ссылок на трек;
- найди места, где платный контент или права могут находиться в клиентском HTML/JS/JSON;
- найди текущие feature flags, env-переменные, миграции и тестовый контур;
- проверь, есть ли `.openai/hosting.json`, Cloudflare Worker, Tilda-страницы или другая фактическая среда;
- зафиксируй обнаруженное в коротком плане реализации.

Не останавливайся после аудита. Если нет блокирующего противоречия, продолжай реализацию в текущем стеке. Не переписывай проект на новый framework только ради этой задачи.

## 2. Источники истины

Используй приложенные файлы в следующем порядке:

1. `spec/MLM_Academy_Track_Router_v2.json` — машинная спецификация;
2. `references/MLM_Academy_Track_Matrix_112_v2.xlsx` — мастер-матрица;
3. `references/Библиотека_онтологии_и_конструкций_треков_v2.xlsx`;
4. приложение A в `references/БТ_на_трекеры_v2.docx`;
5. `references/MLM_Academy_matrix_audit_2026-08-31.md`;
6. HTML-карта — только визуальная справка.

Жёсткие правила:

- импортировать ровно 112 уникальных A-ID;
- импортировать ровно 58 `RouteRule v2` со статусами;
- не переносить 231 legacy-связь в исполняемый Route Engine;
- не создавать связи из поля `legacyNextIds`;
- не считать каждый A-ID отдельной публичной страницей;
- не менять ID и не перенумеровывать реестр.

## 3. Развести пять слоёв системы

Не смешивай их в одном JSON или компоненте.

### 3.1. Registry layer

Хранит стабильную идентичность 112 сущностей:

- `id`;
- `canonicalId`;
- `entityType`;
- `publishSurface`;
- `section`;
- `domain`;
- `title`;
- `situation`;
- `result`;
- `audience`;
- источники;
- текущий implementation status;
- отдельный runtime publication status.

Типы из v2:

- `TRACK`;
- `CONDITIONAL_TRACK`;
- `REMEDIATION`;
- `GATE`;
- `EMBEDDED_TOOL`;
- `SYSTEM_ACTION`;
- `ALIAS`.

### 3.2. Content layer

Хранит версионированное содержание конкретного готового трека. Контент не должен быть обязательной частью записи registry. Отсутствующий контент не ломает реестр.

Полный платный контент нельзя импортировать в публичный клиентский bundle, публичный HTML или публичный JSON. Он должен загружаться только через серверную проверку доступа либо оставаться в server-only модуле/приватном хранилище.

### 3.3. Routing layer

Хранит `RouteRule` и вычисляет следующее назначение только после наблюдаемого outcome.

Поддерживаемые destination types:

- `TRACK`;
- `SYSTEM_ACTION`;
- `FIELD_ACTION`;
- `WAIT_UNTIL`;
- `DONE`;
- `EXPERT`;
- `PROCESS_OWNER`;
- `RETURN_TO_ROUTE`.

### 3.4. Runtime layer

Хранит экземпляр прохождения, outcome, решение маршрутизатора, ожидание и завершение. Шаблон трека и прохождение пользователя — разные сущности.

### 3.5. Access and commerce layer

Хранит серверно проверенную личность, продукт и entitlement. Право на контент и переходы нельзя выводить из URL, query string, localStorage, client-side group, страницы `success` или присланного клиентом email/Member ID.

## 4. Поведение разных entity type

Реализуй единый resolver.

- `TRACK`, `CONDITIONAL_TRACK` — самостоятельная страница только при наличии опубликованной content version и подходящего доступа.
- `REMEDIATION` — самостоятельный on-demand трек; не показывать как обязательную линейную ступень без подтверждённого дефицита.
- `GATE` — проверка внутри родительского трека или Route Engine; не отдельный урок.
- `EMBEDDED_TOOL` — компонент внутри канонического трека; прямой URL ведёт в canonical target/контекст, а не создаёт копию страницы.
- `SYSTEM_ACTION` — системная форма или операция; не учебная страница.
- `ALIAS` — безопасный redirect/resolve на `canonicalId`, без дублирования контента и прогресса.

Защити resolver от alias loop и отсутствующего canonical target.

## 5. Канонические URL

Сейчас рабочая схема проекта и спецификация v2 используют `/track?id=a2-008`. Централизуй это в одной функции, например `trackUrl(trackId)` и одном parser/normalizer.

Требования:

- ID регистронезависим на входе и хранится в каноническом uppercase формате;
- ссылки по проекту не собираются строковой конкатенацией в разных компонентах;
- текущая рабочая ссылка `/track?id=<lowercase-id>` продолжает работать;
- если в репозитории уже надёжно поддержан `/track/<id>`, можно сохранить его как alias/redirect, но нельзя ломать текущие ссылки;
- alias Track ID сначала разрешается через registry, затем проверяется доступ.

## 6. Route Engine

Создай чистый детерминированный модуль без зависимости от UI.

Вход:

```ts
type RouteContext = {
  fromId: string;
  outcomeCode: string;
  facts: Record<string, unknown>;
  userAccess: AccessContext;
  now: string;
  mode: "production" | "pilot" | "admin-preview";
};
```

Выход:

```ts
type RouteDecision = {
  matchedRuleId: string | null;
  destinationType: DestinationType;
  destinationId: string | null;
  reasonCode: string;
  reasonText?: string;
  recovery?: { type: DestinationType; id?: string } | null;
  locked: boolean;
  lockReason?: "AUTH_REQUIRED" | "ENTITLEMENT_REQUIRED" | "FEATURE_DISABLED" | "CONTENT_UNAVAILABLE";
};
```

Правила вычисления:

1. Нормализовать `fromId` и проверить registry.
2. Отобрать правила по `fromId + outcomeCode`.
3. В production использовать только разрешённые статусы правил. `PILOT_DRAFT_TO_TEST` не исполнять вне pilot/admin-preview.
4. Проверить field/operator/value безопасным whitelist evaluator. Никакого `eval`.
5. Сортировать по `priority`, затем по `ruleId` для детерминированности.
6. Если совпали два правила одного приоритета с разными назначениями — вернуть controlled conflict и записать событие, а не выбирать случайно.
7. Сначала применить stop/access constraints, потом выдавать назначение.
8. Если правила нет — вернуть безопасный `DONE`, `RETURN_TO_ROUTE` либо `NEEDS_REVIEW` согласно контракту. Не угадывать следующий Track ID по разделу или `legacyNextIds`.
9. Сохранять snapshot версии правила в `route_decision`, чтобы последующее изменение матрицы не переписало историю.

Route Engine не должен зависеть от того, с какого трека начался маршрут. Любой Track ID может быть входным узлом через entry rule, поиск, назначение, событие или родительский маршрут.

## 7. Backend domain model

Адаптируй `spec/backend-reference-schema.sql` к фактическому стеку. Нужны эквивалентные сущности:

- `track_definitions`;
- `track_content_versions`;
- `route_rules`;
- `entry_rules`;
- `track_instances`;
- `track_outcomes`;
- `route_decisions`;
- `route_assignments`;
- `products`;
- `entitlements`;
- `payment_events`/ledger;
- `import_runs`.

Не применяй production migration без отдельного разрешения. Создай миграции, локально/в тестовой среде проверь их и добавь repository interfaces, чтобы backend не зависел от KV или localStorage.

Критично:

- платные права не хранить только в Cloudflare KV;
- primary production storage должен подключаться через server-side `DATABASE_URL` и быть заменяемым;
- до отдельного решения по размещению и персональным данным не привязывай архитектуру к новому иностранному SaaS;
- пользовательский email не нужен в маршрутных таблицах, используй внутренний `user_id`;
- персональные данные контактов из A2-008 — ФИО, телефон, email, адрес, текст переписки и свободное описание человека — не отправлять на сервер;
- сервер может хранить только минимальный факт: opaque card ID, категориальные outcome-коды, дату, статус и счётчики, если это действительно нужно;
- аналитика не должна содержать исходные сообщения или контактные данные.

## 8. Identity, entitlement и оплата

Сохрани существующую интеграцию Tilda Members, но оберни её в `IdentityProvider`.

Нельзя доверять:

- `ma_id` или `ma_email`, пришедшим из браузера без серверной проверки;
- localStorage;
- query params;
- фронтовой группе доступа;
- возврату пользователя на success page.

Нужна серверная сессия с `HttpOnly`, `Secure`, подходящим `SameSite` cookie. Если текущий Members-контур нельзя серверно проверить, создай адаптер и закрытый stub, но не включай платный доступ.

Entitlement выдаётся только после проверенного server-to-server webhook провайдера оплаты. Webhook должен иметь:

- проверку подписи;
- idempotency key;
- журнал входных событий;
- сопоставление оплаченного продукта;
- атомарную выдачу/обновление entitlement;
- защиту от повторной обработки;
- обработку возврата/отмены.

Сейчас `PAYMENTS_ENABLED=false`. Не подключай боевые ключи и не создавай настоящие платежи.

## 9. Feature flags и текущий доступ

Создай централизованный конфиг с безопасными defaults:

```text
TRACK_REGISTRY_ENABLED=true
ROUTE_ENGINE_ENABLED=true
PAID_TRACK_NAVIGATION_ENABLED=false
PAYMENTS_ENABLED=false
ALLOW_DRAFT_RULES=false
ADMIN_PREVIEW_ENABLED=true
ENTITLEMENT_BYPASS=false
```

`ENTITLEMENT_BYPASS` никогда не должен включаться в production.

Матрица доступа:

- `ANON`: публичная витрина, поиск и разрешённые public metadata; без полного контента, прогресса и маршрутных переходов.
- `FREE`: разрешённые промо-треки/метаданные; без платной маршрутной навигации.
- `START`, `FULL`, `PILOT`: только контент продуктов, на которые есть действующий серверный entitlement, и только когда глобальная навигация включена.
- `ADMIN`: preview draft/metadata через отдельную проверяемую роль; не путать admin preview с пользовательской покупкой.

Права определяются как логическое AND:

```text
global feature enabled
AND authenticated server session
AND active server-side entitlement
AND product grants this track/version
AND content publication status permits access
```

## 10. Публичная витрина и закрытая навигация

Сохрани текущее поведение поиска: запрос выполняется только по кнопке «Найти решение» или Enter, а не на каждый ввод символа.

Публично можно отдавать:

- Track ID;
- название;
- ситуацию;
- обещаемый результат;
- раздел/домен;
- статус `Готовится`, если это уже предусмотрено витриной;
- признак доступности.

Публично нельзя отдавать:

- полный платный контент;
- ответы, шаблоны сообщений и внутренние инструменты платного трека;
- необработанные route facts;
- доступные пользователю transition payloads до проверки entitlement;
- скрытые draft rules, если они раскрывают закрытую механику.

Кнопки следующих действий и переходов не хардкодить в страницах. После outcome страница обращается к серверу, получает `RouteDecision` и рендерит разрешённое действие. Пока `PAID_TRACK_NAVIGATION_ENABLED=false`, обычный пользователь получает locked-state без работающей кнопки перехода. Admin preview может видеть диагностическую схему отдельно.

Угадывание URL не должно открывать контент. Проверка доступа выполняется на сервере для каждого запроса контента и mutation.

## 11. API contract

Адаптируй URL к текущему backend, но сохрани смысловые endpoints:

```text
GET  /api/v1/tracks/:id/meta
GET  /api/v1/tracks/:id/content
POST /api/v1/track-instances
GET  /api/v1/track-instances/:instanceId
POST /api/v1/track-instances/:instanceId/outcomes
GET  /api/v1/me/route
GET  /api/v1/me/entitlements
POST /api/v1/admin/tracks/import/dry-run
POST /api/v1/admin/tracks/import/apply
```

Требования:

- meta может быть публичным только в разрешённом объёме;
- content и runtime endpoints требуют server session и access check;
- outcome mutation идемпотентна по client event ID;
- ответ outcome содержит RouteDecision, но destination URL формируется сервером/общим helper;
- admin import защищён отдельной ролью и не доступен обычному пользователю;
- ошибки доступа имеют единые коды, без утечки закрытого контента.

## 12. Импорт реестра и будущих треков

Не заставляй runtime читать Excel. Excel остаётся мастер-файлом методолога, а приложение получает валидированный JSON.

Создай команды, эквивалентные:

```text
tracks:validate <router-or-package>
tracks:import --dry-run <file>
tracks:import --apply <file>
track:check <track-id>
```

Импорт должен быть:

- schema-validated;
- идемпотентным;
- транзакционным;
- версионированным;
- с dry-run diff;
- с запретом неизвестного destination ID;
- с запретом alias loop;
- с запретом публикации `GATE`, `EMBEDDED_TOOL`, `SYSTEM_ACTION`, `ALIAS` как обычного урока;
- с запретом активации `PILOT_DRAFT_TO_TEST` в production;
- с запретом удаления ID, на которые есть история;
- с журналом import run и checksum.

Для нового трека используй `spec/track-package.schema.json`. Контентная папка должна быть server-only. Если текущий стек TypeScript — создай строгие типы и runtime validation, например через уже установленный валидатор; не добавляй библиотеку без необходимости. В другом стеке используй эквивалент.

## 13. A2-008 как контрольный сценарий, а не корень системы

Сохрани A2-008 как первый тестовый узел, но не делай его корнем всего графа.

Контрольные ветви из v2:

- `NEXT_MESSAGE` → A3-002;
- `NEXT_REFERRAL_REQUEST` → A2-013;
- `NEXT_REFERRAL_CALL` → A3-003 при разрешении;
- `NEXT_SCHEDULE` → A3-005;
- отсутствие настоящего повода → recovery A3-016 или WAIT;
- недостаточно безопасных контекстов → A2-010;
- после полевого действия → A3-008 как `SYSTEM_ACTION`;
- ответ «позже» при разрешении → A5-010 + `WAIT_UNTIL`;
- прямой отказ → A5-014 + `DONE`.

Контактные данные остаются локально. Сервер получает только outcome-коды и минимальные безопасные факты.

## 14. Наблюдаемость без слежки

Добавь структурированные события без персональных данных:

- `track_meta_viewed`;
- `track_access_denied`;
- `track_started`;
- `outcome_submitted`;
- `route_decided`;
- `route_conflict_detected`;
- `wait_scheduled`;
- `route_done`;
- `track_imported`.

Не отправляй в аналитику тексты сообщений, ФИО контактов, телефоны, email и свободные заметки.

## 15. Tests и acceptance criteria

Добавь unit, integration и security tests, соответствующие стеку.

Обязательные проверки:

1. В registry ровно 112 уникальных ID.
2. Импортировано ровно 58 v2 rules; 231 legacy edge не исполняются.
3. Неизвестный destination ID отклоняется.
4. Alias loop отклоняется.
5. `SYSTEM_ACTION`, `GATE`, `EMBEDDED_TOOL`, `ALIAS` не рендерятся как обычный урок.
6. Draft rule не исполняется в production.
7. Два равноприоритетных конфликтующих правила дают controlled conflict.
8. Без entitlement нельзя получить paid content даже по прямому URL/API.
9. LocalStorage/query/success page не дают entitlement.
10. При `PAID_TRACK_NAVIGATION_ENABLED=false` маршрутная кнопка не работает у обычного пользователя.
11. Admin preview отделён от пользовательского доступа.
12. A2-008 выдаёт разные решения для разных карточек/outcomes.
13. Прямой отказ может завершиться в `DONE`; пауза с разрешением — в `WAIT_UNTIL`.
14. При отсутствии правила система не выбирает `legacyNextIds`.
15. Платный контент отсутствует в public bundle/public JSON.
16. Текущий поиск по-прежнему стартует только по кнопке/Enter.
17. Текущий A2-008 и остальные публичные страницы не получают визуальной регрессии от архитектурной миграции.

## 16. Что не менять

Без отдельного основания не меняй:

- дизайн и тексты сайта;
- алгоритм поиска, кроме подключения к registry metadata;
- содержание A2-008;
- домен и публичную навигацию;
- регистрацию пользователей;
- продакшен-конфигурацию;
- провайдера оплаты;
- юридические тексты;
- книги/первоисточники.

Не создавай заглушки с выдуманным обучающим содержанием. Для отсутствующего трека достаточно registry record и корректного статуса доступности.

## 17. Definition of Done

Задача завершена только когда:

- код собирается;
- существующие тесты проходят;
- новые тесты проходят;
- 112 ID импортируются идемпотентно;
- Route Engine проходит fixture tests;
- доступ и content boundary проверены;
- платная навигация и платежи выключены;
- добавлен пример импорта одного фиктивного/тестового track package без изменения соседних страниц;
- создан документ `docs/mlma-track-architecture/IMPLEMENTATION_REPORT.md`.

В отчёте покажи:

1. фактическую архитектуру до/после;
2. список изменённых файлов;
3. миграции и как их запускать локально;
4. env/feature flags без секретов;
5. команды validate/import/test;
6. какие 112 ID и 58 rules загружены;
7. доказательство, что legacy 231 не исполняются;
8. доказательство, что paid content не доступен без entitlement;
9. что пока намеренно выключено;
10. точную процедуру добавления следующего готового трека.

В конце ответа дай короткий итог: `готово / частично / заблокировано`, команды проверки и оставшиеся блокеры. Не заявляй готовность, если тесты или access boundary не доказаны.
