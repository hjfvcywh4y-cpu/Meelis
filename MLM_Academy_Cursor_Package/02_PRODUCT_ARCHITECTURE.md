# Продуктовая архитектура MLM Academy

## 1. Что является продуктом

MLM Academy — не курс и не электронная книга. Это библиотека коротких рабочих треков, соединённых в маршруты по реальным ситуациям партнёра.

Единица продукта — не «урок», а:

`ситуация → действие → подтверждение результата → следующий шаг`

В текущей версии мы создаём только инфраструктуру этой логики. Содержание, шаги и доказательства появятся позже.

## 2. Что видит B2C-пользователь

Пользователь видит:

- свою текущую ситуацию;
- понятный раздел;
- один следующий шаг;
- карточку трека с обещанным результатом;
- личный маршрут;
- историю произведённых результатов;
- продолжение после действия.

Пользователь не видит:

- книгу как структуру продукта;
- номера страниц и исходные названия;
- внутренний приоритет P0/P1/P2;
- способы редакционной переработки;
- B2B-исследования компаний;
- внутреннюю карту маркетинг-плана;
- экономические и лидерские панели.

## 3. Шесть входов библиотеки

Источник правды — `data/sections.json`.

| Код | Короткое имя в навигации | Полное обещание | Количество треков |
|---|---|---|---:|
| A1 | Старт и система | Начать и выстроить свою систему | 16 |
| A2 | Люди и база | Найти людей и собрать рабочую базу | 16 |
| A3 | Первый контакт | Выйти на контакт и начать разговор | 17 |
| A4 | Потребность и решение | Понять человека и предложить решение | 17 |
| A5 | Сомнения и отказ | Пройти сомнения и сохранить движение | 14 |
| A6 | Повтор и рост | Вернуть клиента, расти и работать сильнее | 32 |

Разделы не являются шестью обязательными последовательными курсами. Это шесть дверей. Пользователь может войти сразу в A5, если у него уже есть конкретное сомнение клиента.

## 4. Иерархия содержания

```text
MLM Academy
├── Раздел A1–A6
│   ├── Модуль
│   │   └── Track ID
│   │       ├── метаданные
│   │       ├── версия содержания (позже)
│   │       ├── прохождение пользователя (позже)
│   │       └── артефакт результата (позже)
│   └── связи со следующими Track ID
└── Личный маршрут пользователя
    ├── следующий шаг
    ├── сохранённые треки
    ├── активные прохождения
    └── произведённые результаты
```

`Track ID` стабилен навсегда. Версия содержания хранится отдельно. Если пользователь начал 1.2.0, он должен закончить именно 1.2.0, даже если редактор уже опубликовал 1.3.0.

## 5. Карта экранов

| Маршрут | Задача экрана | Главная кнопка | Ключевые состояния |
|---|---|---|---|
| `/` | Объяснить продукт через рабочий результат | Найти следующий шаг | гостевой / пустая библиотека / опубликованные треки |
| `/start` | Определить текущую ситуацию | Показать мой раздел | не выбрано / выбран раздел / вернуться |
| `/library` | Найти трек по ситуации и результату | Открыть карточку | результаты / ничего не найдено / preview planned |
| `/library/[sectionId]` | Показать логику одного раздела | Выбрать трек | опубликованные / всё готовится / неверный раздел |
| `/track/[trackId]` | Показать один трек и дальнейший ход | Начать / Сохранить / Вернуться | metadata_only / planned / locked / published / not-found |
| `/my` | Вернуть пользователя в действие | Сделать следующий шаг | новый / есть активный / ожидает внешнего действия |
| `/my/route` | Показать путь без ощущения «курса из 112 уроков» | Продолжить | пустой / текущая ветка / завершённый узел |
| `/my/results` | Показать произведённые артефакты | Открыть результат | пустой / список / фильтр по типу |
| `/profile` | Зафиксировать рабочий контекст | Сохранить | новый / заполнен / ошибка |
| `/access` | Объяснить доступ без ложной оплаты | Оставить заявку / Войти | гость / нет доступа / доступ есть |
| `/admin/catalog` | Проверить здоровье реестра | Запустить проверку | valid / warnings / errors; только dev/admin |

## 6. Глобальная навигация

### Для гостя

- логотип;
- С чего начать;
- Библиотека;
- Как это работает;
- Войти;
- основная CTA: «Найти следующий шаг».

### Для участника

- Главная;
- Библиотека;
- Мой маршрут;
- Мои результаты;
- Профиль;
- поиск.

### Мобильная навигация

После входа — нижняя панель из пяти пунктов:

1. Главная;
2. Библиотека;
3. Маршрут;
4. Результаты;
5. Профиль.

На странице трека нижняя панель может сворачиваться, чтобы не спорить с главной кнопкой действия.

## 7. Навигация внутри раздела

Раздел состоит из:

1. названия и обещания;
2. короткой схемы пути из `routeLogic`;
3. модулей раздела;
4. карточек доступных треков;
5. preview-блока будущих треков только в режиме разработки;
6. возврата к выбору ситуации.

Модуль нужен как средство группировки, но не должен выглядеть обязательной учебной ступенью. Не использовать формулировки «урок 1», «урок 2», если между треками нет обязательной зависимости.

## 8. Каталог и поиск

### Публичные фильтры

- раздел;
- ситуация — полнотекстовый поиск по `situation`;
- результат — полнотекстовый поиск по `outcome`;
- формат;
- статус доступности: доступен / готовится, только в preview.

### Внутренние фильтры admin

- P0/P1/P2;
- тип преобразования;
- уровень адаптации;
- статус публикации;
- наличие продолжения;
- ошибки графа.

Не показывать пользователю внутреннюю сложность тегов. Первая версия поиска может быть нормализованным подстрочным поиском по title + situation + outcome + module. Архитектуру оставить готовой к полнотекстовому и смысловому поиску позже.

### Карточка трека

Порядок информации:

1. раздел и Track ID;
2. название;
3. «Подходит, если…» — `situation`;
4. «На выходе…» — `outcome`;
5. формат;
6. статус;
7. кнопка.

Не показывать длительность, если она не задана. Не ставить фиктивные «10 минут».

## 9. Быстрый старт `/start`

Это не психологический тест и не длинная анкета. Один вопрос:

> Что сейчас больше всего мешает вам двигаться?

Шесть ответов соответствуют A1–A6. После выбора:

- показать выбранный раздел;
- дать одну рекомендуемую опубликованную карточку;
- если опубликованных карточек нет — честно показать состояние разработки и дать сохранить раздел;
- сохранить выбор в демо-профиле.

Не спрашивать возраст, доход, квалификацию и семейное положение на первом входе.

## 10. Личный маршрут

Маршрут — не линейная лестница из 112 элементов. Это текущая ветка:

- что уже сделано;
- где пользователь сейчас;
- один следующий шаг;
- какие развилки доступны после него.

На desktop можно использовать вертикальную карту с боковыми ответвлениями. На mobile — простой stepper. Не рисовать полный граф из 112 узлов: он создаст ощущение схемы метро без названий станций.

`data/pilot.graph.json` используется как первая проверочная ветка. Он содержит 16 уникальных узлов и не означает, что эти треки уже наполнены.

## 11. Личный результат и DONE

Будущее правило завершения трека:

`действие выполнено + evidence/артефакт зафиксирован + следующий шаг выбран`

Просмотр текста или видео сам по себе не завершает трек.

Поддерживаемые будущие типы результата:

- `text` — формулировка;
- `list` — база или список действий;
- `message` — отправленное/подготовленное сообщение;
- `audio` — запись;
- `image` — скриншот или фото;
- `link` — опубликованный материал;
- `fact` — отметка совершённого действия;
- `appointment` — договорённость и дата;
- `reflection` — разбор фактов.

Текущая оболочка должна иметь пустой компонент результата и типы данных, но не просить загрузки и не симулировать отправку на сервер.

## 12. Роли

| Роль | Что может | Текущая реализация |
|---|---|---|
| Гость | смотреть публичную витрину и опубликованный каталог | полностью |
| Участник | иметь маршрут, сохранения и результаты | demo/local provider |
| Наставник | видеть согласованный прогресс подопечных | только контракт и feature flag |
| Контент-редактор | проверять метаданные и статусы | dev/admin экран |
| Администратор | управлять доступом и системой | только контракт; без настоящего backend |

Не строить полноценный кабинет наставника сейчас. Но доменная модель не должна считать, что пользователь всегда один и без организации.

## 13. Статусы

### Публикация трека

- `planned` — есть метаданные, содержание не начато;
- `draft` — содержание собирается;
- `review` — редакционная/этическая проверка;
- `published` — можно показывать пользователю;
- `archived` — снят, но история прохождений сохраняется.

### Содержание

- `metadata_only`;
- `draft`;
- `review`;
- `published`;
- `archived`.

### Будущее прохождение пользователя

- `not_started`;
- `in_progress`;
- `waiting_external`;
- `evidence_required`;
- `completed`;
- `abandoned`.

### Доступ

- `undecided`;
- `free`;
- `paid`;
- `organization`;
- `invite`.

`legacyPublicUrl` и сложность URL не являются защитой. Доступ в будущем проверяется по entitlement.

## 14. Рекомендации

Первая версия строго детерминирована.

Порядок:

1. взять `nextTrackIds` завершённого/текущего трека;
2. удалить отсутствующие и недоступные;
3. поднять опубликованные и доступные;
4. учесть выбранный исход действия;
5. выбрать один главный;
6. показать не более трёх альтернатив.

AI не имеет права придумывать Track ID. В будущем AI может только ранжировать заранее разрешённый кандидатный набор и обязан возвращать объяснимую причину.

Если история отсутствует, рекомендация начинается с ответа `/start`, а не с «умной» догадки.

## 15. Слой данных и будущий backend

Сейчас нужны интерфейсы репозиториев:

- `CatalogRepository`;
- `ProfileRepository`;
- `ProgressRepository`;
- `ArtifactRepository`;
- `EntitlementRepository`.

Текущие реализации:

- catalog — JSON/server-only;
- profile/progress/artifact — Local Storage в preview;
- entitlement — mock.

Будущая замена:

- PostgreSQL/Supabase;
- Supabase Auth;
- Storage для evidence;
- RLS;
- Edge Functions для платежных webhook и сервисных операций.

UI и доменная логика не должны напрямую вызывать Supabase. Замена provider не должна требовать переписывать экраны.

## 16. Tilda и домены

Tilda может использоваться как рекламная витрина. Приложение должно работать отдельно на настраиваемом base URL.

Правила:

- не хардкодить `mlmacademy.ru` или `app.mlmacademy.ru` в компонентах;
- внутренние ссылки строить из относительных маршрутов;
- внешнюю Tilda-ссылку хранить в настройке окружения;
- `legacyPublicUrl` не использовать как роутер;
- при будущей миграции поддержать редиректы со старых URL на новый app route.

## 17. События аналитики — только контракты

Подготовить единый `trackEvent()` с no-op/dev реализацией и событиями:

- `view_home`;
- `select_situation`;
- `view_section`;
- `search_catalog`;
- `view_track_card`;
- `open_track_shell`;
- `save_track`;
- `select_next_action`;
- `view_route`;
- `view_results`.

Не подключать внешний сервис аналитики без отдельного решения.

## 18. Производственный контур добавления трека

Позже новый трек должен появляться так:

1. редактор обновляет метаданные;
2. проверяется Track ID и граф;
3. создаётся файл содержания по `future-track-content.schema.json`;
4. содержание получает версию;
5. проходит review;
6. `publicationStatus` становится `published`;
7. существующая оболочка автоматически начинает показывать Track Player;
8. ни одна страница и навигационная ссылка не создаются вручную.

## 19. Критические риски, которые архитектура обязана закрыть

1. **112 статических страниц.** Закрывается единым динамическим маршрутом и JSON.
2. **Мёртвые ссылки после переименования.** Закрывается стабильным Track ID.
3. **Смешение будущего и готового.** Закрывается publication/content status и preview flag.
4. **Утечка внутренних источников.** Закрывается server-only каталогом и sanitizer.
5. **Навигационный тупик.** Закрывается fallback на раздел и библиотеку.
6. **Ложный прогресс.** Не считаем просмотр завершением.
7. **Ранний AI.** Первая рекомендация детерминирована и тестируема.
8. **Зависимость от Tilda.** Ядро живёт отдельно.
9. **Превращение в обычный LMS.** Интерфейс строится вокруг ситуации, действия и результата.
