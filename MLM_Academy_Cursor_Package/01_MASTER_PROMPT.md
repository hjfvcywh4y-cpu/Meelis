# Мастер-промпт для Cursor: оболочка MLM Academy

## 1. Твоя роль

Работай как ведущий продуктовый инженер, архитектор интерфейсов и строгий технический редактор. Твоя задача — **не нарисовать концепт и не сделать набор статических экранов**, а собрать работающую, расширяемую оболочку MLM Academy.

Сначала изучи текущий репозиторий. Если он пустой — создай приложение. Если код уже есть — сохрани существующую архитектуру и пользовательские изменения, затем встрои новую систему без разрушительной перезаписи.

Не останавливайся после плана. План зафиксируй в `IMPLEMENTATION_LOG.md` и затем последовательно реализуй задачу, проверяя каждый этап.

## 2. Что мы строим

MLM Academy — B2C-библиотека обучения через действие для партнёров сетевого бизнеса.

Пользователь приходит не «изучить продажи», а решить конкретную рабочую ситуацию:

- понять, с чего начать;
- найти людей;
- написать или позвонить;
- понять потребность;
- пройти сомнение или отказ;
- сделать follow-up, повтор и разобрать результат.

Главный принцип продукта:

> Не список просмотренных уроков, а история реально произведённых действий, оставленных результатов и следующих шагов.

Информационная цепочка:

`ситуация → раздел → модуль → трек → действие → фиксация результата → следующий трек`

## 3. Жёсткая граница текущей итерации

Сейчас нужно построить **всю оболочку**, но не создавать содержание треков.

Разрешено:

- использовать метаданные из `data/tracks.catalog.json`;
- показывать название, ситуацию, обещанный результат, формат, раздел и статус;
- строить страницы, карточки, фильтры, связи и пустой Track Player;
- создавать типы, схемы и интерфейсы для будущих шагов;
- использовать демо-состояния прогресса только в отдельном preview/dev-режиме.

Запрещено:

- придумывать уроки, тексты, задания, видео, вопросы и сценарии треков;
- подменять пустой контент сгенерированным «полезным материалом»;
- публиковать внутренние источники, страницы книги, приоритет P0/P1/P2, тип переработки и редакторские заметки;
- смешивать B2C с B2B-исследованиями, маркетинг-планом, Leader Cockpit и экономическими KPI;
- строить оплату, AI-рекомендации, настоящую авторизацию и сложную CRM в этой итерации.

## 5. Технологическая рамка

Если репозиторий не задаёт другой совместимый стек, используй:

- Next.js с App Router;
- TypeScript в строгом режиме;
- React;
- Tailwind CSS и CSS variables для токенов;
- Zod или JSON Schema validation для входных данных;
- server-only слой для полного внутреннего каталога;
- Local Storage только для демо-профиля и демо-прогресса;
- Vitest для доменной логики;
- Playwright или эквивалент для ключевых пользовательских маршрутов;
- пакетный менеджер, уже принятый в репозитории; если выбора нет — `pnpm`.

Не привязывай ядро к Tilda. Tilda может остаться внешней рекламной витриной и вести в приложение, но каталог, маршруты, прогресс и Track Player должны жить независимо.

Не хардкодь домен. Все ссылки на трек создавай функцией вида `routeForTrack(trackId)`. Поле `legacyPublicUrl` сохраняется как импортированная справка и не используется для внутренней навигации.

## 6. Архитектура данных

Полный `tracks.catalog.json` содержит внутренние поля. Он должен импортироваться только на серверной стороне.

Создай два типа:

1. `InternalTrackMetadata` — все поля реестра.
2. `PublicTrackMetadata` — только:
   - `trackId`;
   - `sectionId`;
   - `module`;
   - `title`;
   - `situation`;
   - `outcome`;
   - `format`;
   - `nextTrackIds`;
   - `publicationStatus`;
   - `contentStatus`;
   - `visibility`;
   - `access`.

Никогда не отправляй в клиентский bundle и публичный API:

- `priority`;
- `source`;
- `adaptationLevel`;
- `transformationType`;
- `internalNote`;
- `pageStatusRaw`.

Создай серверный адаптер `toPublicTrackMetadata()` и тест на отсутствие внутренних полей.

Каталог неизменяем в рантайме. Любое обновление идёт через новую версию JSON. Не исправляй исходный каталог молча: ошибки выводи в валидатор и `IMPLEMENTATION_LOG.md`.

## 7. Режимы приложения

Нужны два чётко разделённых режима.

### Production

- публично показываются только `publicationStatus = published`;
- треки со статусом `planned`, `draft`, `review`, `archived` не попадают в обычный каталог;
- прямой production-маршрут неопубликованного трека возвращает корректный not-found или недоступность без утечки внутренних данных;
- внутренний приоритет и редакционные поля нигде не видны.

### Preview / development

- доступны все 112 карточек и оболочек;
- на карточке честно показан статус «Готовится»;
- можно переключать демо-роли и демо-состояния;
- preview должен быть явно помечен и не выглядеть как реальная публикация;
- preview включается только через серверный env-флаг, например `ENABLE_CATALOG_PREVIEW=true`, а не через публичный query-параметр.

## 8. Обязательные маршруты

Реализуй минимум:

- `/` — B2C-главная;
- `/start` — выбор текущей ситуации и первого раздела;
- `/library` — каталог;
- `/library/[sectionId]` — страница одного из A1–A6;
- `/track/[trackId]` — универсальная оболочка трека;
- `/my` — личная главная с одним следующим действием;
- `/my/route` — маршрут пользователя;
- `/my/results` — история артефактов и результатов;
- `/profile` — минимальный рабочий профиль;
- `/access` — нейтральная оболочка доступа/тарифа без подключения оплаты;
- `/admin/catalog` — только dev/admin: здоровье каталога и валидация;
- нормальные `not-found`, loading, empty и error states.

Маршруты должны строиться из ID. Канонический URL использует lowercase: `/track/a1-004`, а внутри системы ID хранится как `A1-004`.

## 9. Навигационная логика

Навигация не повторяет главы книги. Пользователь видит шесть дверей по рабочим ситуациям из `data/sections.json`.

На каждом экране должен быть ответ на три вопроса:

1. Где я сейчас?
2. Что я могу сделать здесь?
3. Куда я пойду после этого?

Используй четыре слоя навигации:

- глобальная: главная, библиотека, мой маршрут, результаты, профиль;
- контекстная: breadcrumbs и раздел;
- деятельностная: один главный следующий шаг;
- графовая: `nextTrackIds` и правила из `recommendation.rules.json`.

Нельзя показывать пользователю больше одного главного next action. Альтернатив — максимум три.

Если следующего опубликованного трека нет, не создавай тупик. Покажи:

- «Продолжение готовится»;
- возврат в текущий раздел;
- переход в библиотеку;
- возможность сохранить будущий трек в маршрут в preview-режиме.

## 10. Универсальная оболочка трека

Страница `/track/[trackId]` едина для всех треков. Не создавай 112 отдельных компонентов.

Она должна уметь показывать:

- breadcrumbs;
- Track ID и раздел;
- название;
- ситуацию пользователя;
- обещанный измеримый результат;
- формат;
- статус доступа и публикации;
- место будущего прогресса;
- пустую область будущих шагов;
- блок будущего DONE-результата;
- рекомендации продолжения;
- состояние `metadata_only` с честным сообщением, что содержание ещё не добавлено.

Не показывай фиктивную шкалу 0/5 шагов, если шагов нет. В состоянии `metadata_only` прогресс скрыт, а не равен нулю.

Подготовь компонентные интерфейсы Track Player для будущего, но не создавай контент:

- `TrackHeader`;
- `TrackProgress`;
- `TrackStepNavigation`;
- `TrackStepViewport`;
- `TrackEvidencePanel`;
- `TrackCompletionPanel`;
- `NextTrackRecommendations`.

## 11. Личный кабинет без ложного прогресса

В текущей версии личный кабинет работает на demo/local provider и обязан иметь хорошие пустые состояния.

Главный экран `/my` показывает:

- одно следующее действие;
- текущий выбранный раздел;
- сохранённые треки;
- последние результаты, если они есть;
- понятный старт, если истории ещё нет.

Не делай KPI вида «просмотрено 63% курса». Будущая единица прогресса — действие и артефакт.

`/my/results` должен быть готов к типам артефактов:

- текст;
- список;
- сообщение;
- аудио;
- изображение/скриншот;
- ссылка;
- отметка факта;
- договорённость со следующим сроком.

Но в этой итерации показывай только пустое состояние и контролируемые demo fixtures в preview.

## 12. Дизайн

Строго соблюдай `03_DESIGN_SYSTEM.md` и визуальный характер `reference/design-reference.html`.

Ключевой образ: не онлайн-университет и не SaaS с фиолетовым градиентом, а **рабочая карта действий** — редакционная сетка, тёплый бумажный фон, чёрные линии, крупная типографика и шесть функциональных акцентов.

Обязательно:

- плотная типографическая иерархия;
- видимая, но спокойная модульная сетка;
- чёрные контуры 1–2 px;
- карточки без теней и стекла;
- один акцент раздела на карточке;
- хорошие focus states;
- адаптивность 360 / 768 / 1440 px;
- reduced motion;
- русский интерфейс без канцелярита и учебникового тона.

Запрещено:

- градиенты;
- glassmorphism;
- неоновые свечения;
- случайные 3D-объекты;
- изображения «успешных людей с ноутбуками»;
- эмодзи как системные иконки;
- конфетти, баллы, лидерборды и детская геймификация;
- гигантские скругления и одинаковые SaaS-карточки;
- декоративные «AI sparkles».

## 13. Порядок реализации

Работай по этапам и после каждого запускай доступные проверки.

### Этап 0. Аудит

- изучить репозиторий;
- зафиксировать стек, команды и ограничения в `IMPLEMENTATION_LOG.md`;
- проверить каталог: 112 уникальных Track ID, валидные разделы и все `nextTrackIds` существуют.

### Этап 1. Основание

- дизайн-токены;
- типы и схемы;
- server-only catalog loader;
- публичный sanitizer;
- route helpers;
- базовый shell, header, mobile navigation, footer;
- preview flag.

### Этап 2. Публичная навигация

- главная;
- `/start`;
- библиотека;
- страницы шести разделов;
- поиск и фильтры;
- карточка трека;
- loading/empty/not-found.

### Этап 3. Личный контур

- `/my`;
- `/my/route`;
- `/my/results`;
- `/profile`;
- local/demo repositories;
- один next action и не более трёх альтернатив.

### Этап 4. Track Player shell

- универсальная страница по ID;
- состояния planned / metadata_only / locked / published-empty;
- компоненты будущего проигрывателя;
- рекомендации по графу;
- без содержания шагов.

### Этап 5. Контроль

- `/admin/catalog` в dev/admin режиме;
- автоматические тесты схемы, уникальности и графа;
- responsive и accessibility-проверка;
- lint, unit tests, e2e smoke tests, production build;
- финальное обновление `IMPLEMENTATION_LOG.md`.

## 14. Что предоставить по завершении

В финальном ответе Cursor должен перечислить:

- что реализовано;
- какие маршруты готовы;
- какие команды запускать;
- результаты lint/tests/build;
- какие env-переменные нужны;
- какие ограничения остались именно потому, что внутренние треки пока не добавлены;
- точный следующий шаг для подключения первого содержательного трека без изменения оболочки.

Результат считается готовым только после выполнения `04_ACCEPTANCE_CRITERIA.md`.
